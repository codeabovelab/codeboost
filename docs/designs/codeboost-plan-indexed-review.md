## Summary

- **What codeboost is.** A local app that takes GitHub issues, helps you write a detailed plan with Claude or Codex, runs the plan with an AI agent, and opens a pull request (PR).
- **What makes it different.** You review the PR one **plan item** at a time. Pick a plan item on the left and see only its code on the right. Code that belongs to no plan item is flagged in a red "Unplanned changes" row.
- **Why that matters.** Other tools make you read a raw diff and guess what the agent meant. In codeboost, the plan you approved is the index to the code.
- **How it stays trustworthy.** codeboost makes every git commit itself, so it knows which plan item produced each line. It also checks each change against the files the plan item said it would touch.
- **How it stays safe.** Agents run in a sandbox with no network and no access to your credentials. Dependency and script changes need your approval.
- **What we build first.** The review screen, tested on real PRs. We build the rest (running agents, the queue, the issue list) only if the review screen proves its worth.

## Terms used

| Term | Meaning |
|---|---|
| Plan | A list of plan items for one GitHub issue. Each plan has a revision number (r1, r2, …). |
| Plan item | One change in the plan, with an ID such as P1. It lists the files it will change and how to check it. |
| Declared files | The files a plan item says it will change. |
| Invocation | One run of an AI agent (Claude or Codex) on one task. |
| Trailer | A line at the end of a git commit message, such as `Plan-Item: P1`. |
| Hunk | Git's name for one block of changed lines in a diff. |
| Segment | Part of a hunk where every line came from the same plan item. codeboost shows segments, not whole hunks. |
| In scope | A change that is in one of its plan item's declared files. |
| Unplanned change | A change that codeboost did not make for any plan item. |
| Ambiguous change | A change that more than one plan item touched, so codeboost cannot say which one owns it. |
| Approval | Your sign-off on one plan item. It records exactly which lines you saw. |
| Stale approval | An approval whose lines have since changed. You must review that plan item again. |
| Run window | A time when codeboost may run tasks, such as weeknights 22:00–06:00. |
| Sandbox | An operating-system limit on what an agent can read, write, and reach over the network. |

## The problem

You want to hand GitHub issues to an AI agent without losing control. Today you read an issue, prompt an agent, and get a PR. Then you read a raw diff and try to work out what the agent meant to do.

codeboost keeps your approved plan in control from start to finish. It follows the 9 steps you described:

1. List the GitHub issues for a repo, most critical first.
2. Write a plan for an issue, with help from Claude or Codex.
3. The plan says exactly what changes, file by file.
4. Approved plans go into a task queue. You can reorder or cancel tasks.
5. You choose when the queue runs and when it stops. When it stops, the task already running finishes.
6. The agent carries out the plan, reviews its own work in rounds until nothing is found, then opens a PR.
7. You review by plan item: pick one on the left, see its code on the right.
8. You can ask the agent about a plan item, or ask for changes to it.
9. You approve, and the PR merges. Or you reject, and the task goes back to the queue with your feedback.

## Why this is worth building

**The plan becomes the index to the diff.** Other tools use the plan only before the work starts. After that, you review the diff on its own. In codeboost, the plan items act as the table of contents for the PR.

**It targets why agent PRs fail.** A 2026 study of 33,596 agent-made PRs, "Where Do AI Coding Agents Fail? An Empirical Study of Failed Agentic Pull Requests in GitHub" ([arXiv:2601.15195](https://arxiv.org/abs/2601.15195)), found that unmerged PRs tend to change more code and often don't match how the team works. Developers also report two other failures: agents change files the task did not need (scope creep), and agents fix issues that another PR already fixed. We treat all of these as ideas to test, not as proven rankings.

**Approvals expire when the code changes.** This idea came from the outside reviewer. When you approve plan item P1, codeboost records the exact lines you saw. If a later revision changes those lines, the approval becomes stale. Next time, you see only what changed since you approved. So rejecting and revising stays quick. You never have to re-read everything.

## Limits we work within

- **One user, one machine.** codeboost uses the `claude` and `codex` tools you already have installed and signed in, plus `gh` for GitHub. It stores no API keys and runs no server on the internet.
- **Agent tools change often.** Their options and output formats change. So the code that talks to each agent is small and versioned.
- **Easy to install.** It is open source. It must install with one command and no compiler.
- **Safe by default.** It runs without you watching, on text from GitHub issues that anyone may have written. See "Keeping unattended runs safe."

## Assumptions we agreed on

1. **The value is in the review, not the queue.** Many tools already turn issues into PRs: issue-orchestrator, Agent Orchestrator, Bernstein, NEEDLE, no_human, and GitHub's own Copilot agent. So codeboost keeps its queue simple and puts its effort into steps 7 to 9.
2. **Two separate signals link code to plan items.** This assumption was changed after the outside review. Signal 1 is the commit trailer. Signal 2 is the plan item's declared files. The review screen shows three separate checks for each plan item: attributed, in scope, and correct. Ambiguous changes are always shown as ambiguous. codeboost never guesses an owner.
3. **Local and single-user.** You start codeboost from the command line. It opens in your browser.
4. **Rejecting revises the same PR.** Your feedback attaches to plan items. The plan gets a new revision. The agent redoes only the affected plan items.

## What an outside reviewer said

We asked Codex (OpenAI's agent) to read a summary of this session cold. Its main points:

- **The best version:** every plan item is a claim you can check, with its code, its tests, and its links to other plan items. Approvals expire when their evidence changes.
- **What excites you most:** your step 7, "User reviews by selecting each specific change in the plan on the left." Build that first.
- **An existing tool to learn from:** [natiixnt/AgentDiff](https://github.com/natiixnt/AgentDiff). It is MIT-licensed, written in Python, and compares a plan with a diff. We confirmed it exists. It has 1 star, so it is an early prototype. It lacks plan revisions, reliable links from code to plan items, per-item feedback, and approvals tied to exact code.
- **An assumption it challenged:** trailers alone cannot catch scope creep, because a trailer only records what the agent claimed. We agreed and changed assumption 2.

Where we disagreed: the plan format is what makes code-to-item links possible. So we design it on day one, even though the planning screen comes later.

## What we will build

We build all 9 steps as one local app. We start with the review screen. After the first two build steps, we stop and check whether the review screen works (see "Build order and the go/no-go check").

### Tools and storage

These are proposals. The engineering review will confirm them.

- **Language:** TypeScript. A Node server and a React user interface, shipped as one npm package.
- **Storage:** SQLite. It holds tasks, plan revisions, approvals, feedback, the schedule, and a run log. **SQLite is the only master copy of each plan.**
- **Storage code:** All database access goes through one small module. By default it uses Node's built-in `node:sqlite`, on the Node versions we test in continuous integration (22.13 and later). That feature is still marked experimental, so we wrap it and hide its warning. If it is missing or fails a start-up check, codeboost uses `sql.js` instead, which needs no compiler.
- **Workspaces:** each task gets its own `git worktree`. codeboost never touches your own checkout.
- **Agents:** one small adapter per agent: `claude -p` and `codex exec`. Each takes a prompt, a worktree, and a set of permissions, and reports progress as it runs.
- **GitHub:** codeboost uses `gh` for issues, PRs, and merging. **Only codeboost runs `gh`. Agents never do.**

### The plan format

Each plan looks like this:

```yaml
issue: 412
revision: 3
items:
  - id: P1
    title: Preserve idempotency key across retries
    intent: <why, in one or two sentences>
    files: [src/http/retry.ts]            # declared files (signal 2)
    changes: <what changes, file by file>
    acceptance:
      - cmd: pnpm test -- retry.test.ts   # a command codeboost runs
      - check: key is set on every attempt, not only the first   # the review agent judges this
    depends_on: []
```

**Where the plan lives.** The plan is not committed to the PR branch. Instead, codeboost writes it into the PR description, between two markers: `<!-- codeboost:plan:start -->` and `<!-- codeboost:plan:end -->`.

- codeboost rewrites only the text between the markers, on each new revision. It also adds a PR comment such as "plan r3."
- codeboost never changes text outside the markers.
- If someone edits between the markers on GitHub, codeboost replaces that text and saves the old text in the task's log.

This keeps the plan out of the code, and there is only one master copy.

### How codeboost runs a plan

**codeboost makes every commit.**
- For each plan item, codeboost runs one agent invocation. It tells the agent not to commit.
- When the invocation ends, codeboost commits the changes itself. It adds two trailers: `Plan-Item: P<n>` and `Plan-Revision: r<k>`.
- If the agent commits anyway, codeboost undoes those commits (keeping the changes) and commits them again with its own trailers.
- So a trailer is a fact codeboost saw, not a claim the agent made.
- If a plan item produced no changes, codeboost marks it "planned but unchanged."

**Review rounds.**
1. After all plan items run, a separate review agent checks each plan item against its intent and its `check:` entries. This agent can read but not edit.
2. codeboost runs every `cmd:` entry on the final code.
3. Each problem found is filed against one plan item. If a problem spans several plan items, it is split into one problem per plan item.
4. codeboost fixes each problem with a new invocation for that plan item. The fix commit carries that plan item's trailer.
5. Rounds stop when a round finds nothing, or after 3 rounds. After 3 rounds, the task moves to **needs human**.

**When the plan is wrong.** A plan item's invocation may edit only its declared files. If it needs another file, it must stop and propose a plan change: the file, the reason, and the new plan item text. Then codeboost:
1. saves the partial changes with the proposal, for reference only;
2. resets the worktree to the last codeboost commit, so nothing partial is kept;
3. moves the task to **needs amendment** and frees the queue for other tasks;
4. waits for you to approve or edit the proposal on the planning screen. Your approval creates the next plan revision;
5. puts the task back in the queue at its old position, and re-runs that plan item from the start.

If an invocation finishes normally but edited an undeclared file anyway, codeboost still commits the change. The change shows on that plan item's row, marked out of scope.

**Checking whether the issue is already fixed.** Before it opens the PR, and again before merging, codeboost checks:
- whether something other than this task's PR closed the issue;
- whether GitHub shows other open or merged PRs that link to the issue;
- whether new commits on the base branch mention the issue number.

It ignores this task's own PR, any draft PRs it opened earlier, and its own commits. If any check matches, the task moves to **possibly already fixed**. codeboost does not open a PR. You choose to continue, or to cancel and delete the workspace.

### Keeping unattended runs safe

**Issue text is untrusted.** Anyone may have written it. So codeboost puts issue text inside a clearly marked data block in each prompt, and tells the agent it is data, not instructions. The agent follows only the plan items you approved.

**Which issues can be queued.**
- By default, only issues written by repo collaborators.
- Other issues need you to click "trust this issue." codeboost records that choice.

**Which comments reach the agent.**
- By default, only comments from repo collaborators.
- If you chose "trust this issue," comments from other people are included too, inside the same data block.
- Every invocation records which comments it was given.

**The sandbox (the real safety boundary).** Every invocation that can edit files or run commands runs inside the agent's own operating-system sandbox. That is Codex's `--sandbox workspace-write` mode and Claude Code's sandbox mode, on macOS and Linux. In the sandbox:
- the agent can write only inside the task's worktree;
- the network is off;
- `HOME` points to an empty folder for the task;
- reading credential folders is blocked, including `~/.ssh`, `~/.config/gh`, `~/.npmrc`, `~/.aws`, and `~/.docker`;
- git's credential helper is turned off.

If the sandbox does not work on your computer, codeboost refuses to run tasks while you are away. You can still run tasks while you watch.

**Changes that need your approval.**
- **Dependencies.** Only codeboost installs them, as a separate step with the network on. If a task changed a package manifest or lock file, codeboost first stops and shows you the change. It waits in **needs approval**.
- **Scripts.** If a task changed a script that codeboost is about to run (`package.json` scripts, a Makefile, CI settings, or test settings), codeboost stops in **needs approval** before running it.

**Permissions by phase.**

| Phase | Can edit files | Can run commands | Network |
|---|---|---|---|
| Planning, questions | No | No | Agent's own connection only |
| Carrying out and fixing | Worktree only | Allowed list only (test, lint, build) | Off |
| Reviewing | No | `cmd:` checks only | Off |

The allowed list comes from your repo's scripts, and you can edit it. It stops accidents. It does not stop a hostile agent: an agent could edit a script and then run it. The sandbox and the approval step are what stop that.

**Credentials.** codeboost also removes `GH_TOKEN`, `GITHUB_TOKEN`, and other secret-looking variables from the agent's environment. Only codeboost itself is signed in to GitHub.

**Known limits.** The README states these plainly:
- The agent tool can always reach its own sign-in (your Claude or Codex account).
- The sandbox is built by the agent's vendor, so its guarantees are theirs.
- Installing dependencies runs their install scripts with the network on. That is why it needs your approval.

### How codeboost links code to plan items

**It follows each commit, not only the final code.** For every commit in the task, codeboost records which lines it added and removed, and which plan item the commit belongs to. Then it traces each line of the final diff back to the commit that last changed it.
- An added line belongs to the commit that added it.
- A removed line belongs to the commit that removed it. So even changes that only delete code have an owner.
- A line changed by commits from two or more plan items is marked **multi-item**.

**It shows segments, not whole hunks.** codeboost splits each hunk wherever the owner changes. For example, a hunk with some lines from P1 and some from P2 becomes two segments: one on P1's row, one on P2's row. Both carry a "shares a hunk with P1/P2" label.

**Where each segment goes.** First find who made the segment (rows). Then find whose declared files it is in (columns).

| Who made it | In no plan item's files | In only this plan item's files | In other plan items' files only | In several plan items' files, including this one |
|---|---|---|---|---|
| One plan item (Px) | Px row, **out of scope** | Px row, **in scope** | Px row, **out of scope**, naming the owner | Px row, **in scope**, labeled "shared file" |
| Several plan items | **Ambiguous** row | **Ambiguous** row | **Ambiguous** row | **Ambiguous** row |
| Not codeboost (for example, someone pushed to the branch) | **Unplanned** row | **Unplanned** row | **Unplanned** row | **Unplanned** row |

So the red "Unplanned changes" row holds only changes codeboost did not make. When an agent works outside its declared files, the change stays on that plan item's row, marked out of scope. That way you can see which plan item did it.

**The three checks on each plan item.**

| Check | Green | Warning | Grey |
|---|---|---|---|
| Attributed | None of this plan item's lines are in the Ambiguous row. | Amber: some are. The chip links to them. | No changes |
| In scope | Every segment is in a declared file. | Red: some are not. The chip lists the files. | No changes |
| Correct: tested | Every `cmd:` check passes on the latest code. | Red: one fails. | "n/a": no `cmd:` checks |
| Correct: reviewed | No open problems. | Shows the number of open problems. | — |

A plan item with no changes can be approved only if you confirm "no change needed." codeboost records that.

**What an approval records.** When you approve a plan item, codeboost saves its changes: for each file, the added and removed lines in order. It leaves out line numbers and surrounding lines. The only thing it adjusts is line endings (Windows to Unix). Spaces and tabs count. So:
- a whitespace-only change to approved code makes the approval stale. This matters in Python, YAML, Makefiles, and text strings;
- code that only moved up or down, because of other plan items or a rebase, keeps its approval.

**Changes since you approved.** For a stale plan item, the review screen opens on "Changed since approval." It shows the difference between what you approved and what is there now.

**Assigning ambiguous or unplanned changes.** You can assign a segment in the Ambiguous or Unplanned row to a plan item, or accept it as it is.
- codeboost remembers your choice by file and exact content. The choice survives new revisions, re-runs, and rebases, as long as that content does not change. If the content changes, the choice lapses.
- Assigning a segment adds it to that plan item. So that plan item's approval always becomes stale, and you approve it again with the segment included.
- Accepting a segment as it is creates a separate approval, which goes stale by the same rule.

### Asking questions and requesting changes (step 8)

**Questions.** You get an answer right away, at any time, even outside run windows. The agent can read but not edit. It sees the plan item, its current code, its open problems, and the conversation so far. A question never creates a new revision.

**Change requests.** Nothing happens until you click "Reject with feedback." Then codeboost:
1. collects all your change requests into the next plan revision;
2. marks the affected plan items to run again;
3. puts the task back in the queue. It runs only during run windows;
4. re-runs only those plan items. Each fix commit carries its plan item's trailer;
5. runs the review rounds again.

Approvals on other plan items stay valid, as long as their code did not change.

### Approving and merging (step 9)

**When you can merge.** "Approve & merge" works only when all of these are true:
- every plan item is approved, and no approval is stale;
- the Ambiguous and Unplanned rows are empty, or you assigned or accepted every segment in them;
- every plan item's `cmd:` checks pass on the latest code, or it has none;
- no plan item has open problems, or you marked each open problem "accepted";
- GitHub's required checks pass on the latest code;
- the "already fixed" check finds nothing.

The top of the screen lists anything that is not yet true. You can still use "Merge anyway." It asks you to confirm, and codeboost records it.

**What happens when you click "Approve & merge".**
1. codeboost fetches the latest base branch.
2. If the base has not moved since GitHub's checks last passed, it goes straight to step 5.
3. If the base has moved, codeboost rebases the PR branch (see below) and pushes it. If the rebase changed any plan item's code, codeboost stops and sends you back to review those plan items.
4. codeboost waits for GitHub's required checks on the new code. The screen shows their progress. If they take longer than 30 minutes, the task moves to **approved, merge blocked**.
5. codeboost runs the "already fixed" check again, then merges.

codeboost also rebases before it first shows you the review. So you always review code that sits on the latest base.

**How rebasing works.** A rebase that goes cleanly keeps your approvals, because approvals ignore line numbers. If there is a conflict:
1. Git stops on one commit. Every commit belongs to exactly one plan item, say Px.
2. codeboost runs a sandboxed invocation to fix the conflict. The agent sees Px's plan item, the conflicting files, and the base commits that caused the conflict. It may edit only the conflicting files.
3. The fixed commit keeps Px's trailers.
4. If the fix needs another file, or the invocation fails, codeboost cancels the rebase (`git rebase --abort`). That puts the branch back as it was. The task moves to **needs human**.
5. Any plan item whose code changed in the fix gets a stale approval.

If codeboost is stopped or crashes during a rebase, it always cancels the rebase first when it recovers.

**Merge method.** By default, codeboost uses a merge commit. This keeps every plan item's commits and trailers in the repo history. You can choose squash for a repo instead. Then the squash message lists each plan item and its trailers, but the line-by-line links live only in codeboost's database.

**When GitHub refuses the merge.** For example, a rule may require a second reviewer, a check may be blocked, or there may be a conflict. Then codeboost shows GitHub's exact error, and the task moves to **approved, merge blocked**.

**Checking branch rules.** When you add a repo, codeboost reads its branch rules through GitHub's rulesets API. That needs only read access. If that fails, it tries the older branch-protection API. If both are refused, the rules show as "unknown," and codeboost learns them from the first merge. codeboost 1.0 does not support rules that require a second human reviewer, and it warns you about them when you add the repo.

### The queue, stopping, and recovery (steps 4 and 5)

**Run windows.** You can start and stop the queue by hand. You can also set weekly times, such as weeknights 22:00–06:00. codeboost 1.0 runs one task at a time.

**Stopping (your step 5).** When you click stop, or a run window ends, the running task finishes. It keeps going until it opens its PR or reaches a state that needs you (needs human, needs amendment, needs approval, or possibly already fixed). No new task starts. A task that is waiting for you never blocks the queue.

**Time and round limits.** Each task has limits so that "finishing" cannot run forever. The defaults are 2 hours and 3 review rounds, and you can change them. When a task hits a limit, it moves to **needs human**.

**Stopping right now.** "Hard stop" ends the agent at once. codeboost cancels any rebase, then resets the worktree to its last commit. Later, the task continues from the next unfinished plan item.

**After a crash, sleep, or restart.** When codeboost starts, any task that was running is reset to its last commit and put first in the queue. codeboost reuses the task's worktree if it is intact, and otherwise rebuilds it from the branch.

**Needs human.** codeboost opens a draft PR with the plan in its description. The review screen shows the open problems on their plan items. You can:
- review it anyway, treating the problems as known;
- add guidance and send it back to the queue. Your guidance becomes feedback for the next revision;
- cancel. codeboost closes the draft PR and deletes the worktree.

### Build order and the go/no-go check

1. **Plan format and linking engine.** A code library, tested with sample git histories.
2. **Review screen.** It works on any branch whose commits carry trailers, with a plan loaded into the database. It covers steps 7 to 9: the merge rules and merging through `gh`.
3. **Go/no-go check.** Run the real-PR test in "How we will know it works." Continue only if reviewing by plan item wins. If it does not, change the linking design, or switch to option C, before building anything that runs agents.
4. **Running agents.** Worktrees, agent adapters, permissions, one invocation per plan item, review rounds, the "already fixed" check, and opening PRs (step 6).
5. **Planning screen.** Writing plans with an agent, and approving plan changes (steps 2 and 3).
6. **Queue, schedule, and recovery** (steps 4 and 5).
7. **Issue list, sorted by how critical each issue is** (step 1).

## Open questions

- **How to rank issues (step 1).** Possible inputs: labels such as `P0`, `bug`, and `security`; reactions and comment counts; age; and an AI triage score. Each issue should say why it ranks where it does, for example "ranked high: security label and 14 reactions." The weights are not decided.
- **Running several tasks at once.** Version 1.0 runs one task at a time. Running several needs a way to spot two tasks that plan to change the same files. This is postponed.
- **A different agent for each phase.** For example, Codex could review Claude's work. The adapters allow this. The settings screen is postponed.
- **Reusing AgentDiff.** Read its code before build step 1, and decide whether to borrow from it.
- **A stronger network sandbox.** A later version might run agents in a container that can reach only package registries.

## How we will know it works

**Test cases for build step 1.** The tests must cover all of these:
- two plan items;
- an agent editing a file its plan item did not declare. Expected: shown on that plan item's row as out of scope;
- a change pushed without a trailer. Expected: shown in the Unplanned row;
- a change that only deletes lines. Expected: owned by the plan item that deleted them;
- one line changed by two plan items. Expected: shown in the Ambiguous row, with both plan items' "Attributed" checks amber;
- one hunk with lines from two plan items. Expected: split into two segments, each labeled as sharing a hunk;
- a new revision that changes one approved plan item. Expected: only that approval goes stale;
- a rebase that only moves lines. Expected: no approval goes stale;
- a whitespace-only change to approved code. Expected: that approval goes stale;
- assigning an Unplanned segment to a plan item. Expected: that plan item goes stale, and the assignment survives an unrelated revision;
- the "already fixed" check run against the task's own PR. Expected: no match.

**The real-PR test (the go/no-go check).**
1. Pick two similar small issues in a repo you own.
2. Make both PRs by hand, using the method in "The assignment" below. (Build step 4 does not exist yet.)
3. Before you review, run a small script, `scripts/plant.ts`. It adds one out-of-scope change at a random place in each PR, and saves the places in a sealed file. Open that file only after you decide on each PR.
4. Review one PR as a raw diff on GitHub, and the other in codeboost. Time each review, from opening to deciding.
5. Count the changes you could not explain from the plan or the diff.

The check passes if the codeboost review is no slower, leaves no change unexplained, and finds the planted change.

**Unattended runs.** Queue 3 issues, set a run window, and walk away. When you come back, each task has either a PR ready for review or a clear state (needs human, needs amendment, or possibly already fixed). This holds even if the laptop slept during the run.

**Rejecting.** Reject with feedback on one plan item. The next revision changes only that plan item's code, and every other approval stays valid.

## How people will install it

- **One command.** Run `npx codeboost` inside a repo. It starts the local server and opens the app in your browser.
- **Requirements.** A Node version in the range we test (22.13 or later). codeboost checks for `git`, a signed-in `gh`, and at least one of `claude` or `codex`. It tells you what is missing.
- **No compiler needed.** It has no native modules. It uses `node:sqlite`, or `sql.js` as a fallback.
- **Releases.** GitHub Actions runs all tests on every PR. When we tag a version, it publishes to npm and creates a GitHub release.
- **Later, maybe:** a Homebrew formula.

## Reviewer Concerns

### R2-1 — feasibility

**Problem**

> The Execute/fix shell allowlist (test, lint, build, package install) is not a real boundary: the same agent can edit test files, package.json scripts, Makefile targets, or add dependencies with install scripts in the worktree, then run an allowlisted command that executes that code. With no network sandbox, this yields arbitrary code execution and egress on the user's machine from an agent steered by untrusted issue text, which conflicts with the 'safe by default' constraint.

**Remedy**

> State the allowlist's real guarantee honestly (it limits accidental commands, not a hostile agent), and either add a containment layer for execute/fix (OS sandbox or container, or Claude/Codex sandbox modes with network off except during a codeboost-run install step) or require user approval before running commands whose definitions the agent changed in this task (script, Makefile, lockfile, dependency changes).

### R2-2 — completeness

**Problem**

> Credential protection only strips environment variables. File edits are limited to the worktree, but file reads and allowlisted commands can still reach ~/.config/gh/hosts.yml or the OS keyring-backed gh token, ~/.ssh, ~/.npmrc, cloud credential files, and the git credential helper, so 'gh auth stays with codeboost's own process' is not enforced.

**Remedy**

> Define read restrictions for agent invocations (deny paths outside the worktree, or run with a separate HOME/credential-free profile) and document which credential stores remain reachable in v1 as a known limit.

### R2-3 — completeness

**Problem**

> Eligibility is decided by the issue author, but comments from non-collaborators on an eligible issue still flow into planning and execution prompts, so untrusted text reaches the agent without the 'trust this issue' action.

**Remedy**

> State whether non-collaborator comments are excluded, included only after explicit trust, or included in the delimited data block, and record which comments were supplied to each invocation.

### R2-4 — feasibility

**Problem**

> The superseded check looks for gh timeline cross-references to open or merged PRs, but codeboost's own PR (and a needs-human draft PR) cross-references the issue, so the pre-merge check would match itself and move every task to 'possibly superseded'.

**Remedy**

> Exclude the task's own PR (and its prior draft PRs) and its own branch commits from all superseded signals, and add this case to the tests.

### R2-5 — feasibility

**Problem**

> codeboost rebases onto the current base right before merge, which force-pushes the branch and restarts CI; the merge gate requires required checks to pass, so merge is blocked (or races pending checks) immediately after the rebase. The waiting behavior and whether the rebase happens on 'Approve & merge' click or earlier is undefined.

**Remedy**

> Define the pre-merge sequence: rebase and push, wait for required checks on the new head (with timeout and UI status), re-run the superseded check, then merge; or merge only if the base has not moved since checks last passed.

### R2-6 — feasibility

**Problem**

> Rebase-conflict handling says 'an invocation scoped to the conflicted items' but git rebase stops per replayed commit. The document does not state the permission profile, which trailer the resolved commit keeps, how a conflict spanning several items' commits is handled, or how a hard stop or crash mid-rebase is recovered.

**Remedy**

> Specify the conflict protocol: when codeboost pauses the rebase, what context and profile the agent gets, that the resolved commit keeps the original commit's trailers (or a new trailer rule), handling of multi-item conflicts, and rebase --abort on stop or crash recovery.

### R2-7 — completeness

**Problem**

> On a scope escape the invocation stops and returns a plan_amendment, but the document does not say what happens to the partial edits that invocation already made in declared files: committed under the item's trailer, discarded by reset, or kept uncommitted in the worktree while the task waits.

**Remedy**

> Choose one behavior (e.g., reset the worktree to the last codeboost commit and re-run the whole item after the amendment is approved) and state it.

### R2-8 — clarity

**Problem**

> Provenance is defined per line (a line changed by several items is multi-item), but classification is per final hunk. A hunk can contain adjacent lines from different single-item commits without any single line being multi-item; its row and chips are undefined.

**Remedy**

> Define hunk provenance from its lines (e.g., a hunk whose lines come from more than one item goes to Ambiguous, or hunks are split at provenance boundaries) and add a fixture for adjacent lines from two items.

### R2-9 — completeness

**Problem**

> Merge-gate decisions that assign an Ambiguous or Unplanned hunk to an item or accept it as-is are recorded, but their persistence across revision r+1, re-execution, and rebases is undefined, and it is not stated whether an assigned hunk becomes part of the item's approval snapshot.

**Remedy**

> State the identity used to carry assignment/accept decisions forward, when they are invalidated, and whether assigned hunks enter the target item's content hash.

### R2-10 — consistency

**Problem**

> The approval snapshot is whitespace-normalized, yet the document says only a change to the item's own added or removed lines invalidates approval. A whitespace-only change to approved code (significant in Python, YAML, Makefiles, string literals) would not invalidate the approval, so the user can merge code they did not see.

**Remedy**

> Restrict normalization to what cannot change semantics (e.g., line endings and trailing whitespace only), or state the accepted risk and exclude whitespace-significant files from normalization.

### R2-11 — clarity

**Problem**

> The Attributed chip is defined as green when every hunk in the row has single-item provenance and amber for shared-file, but the classification table sends every multi-item and no-trailer hunk to other rows, so every item row is single-item by construction. The chip therefore never signals missing attribution, and 'shared-file' overlaps with the In-scope judgment the premise says is kept separate. The chip state for a planned-but-unchanged item is also undefined.

**Remedy**

> Redefine the Attributed chip so it can fail (e.g., amber/red when the item has hunks in the Ambiguous row) or drop it, move the shared-file marker to the scope judgment or a hunk badge, and define chips for items with no hunks.

### R2-12 — clarity

**Problem**

> The merge gate does not include the Correct signals, so failing cmd: acceptance commands or open review findings (e.g., after 'review anyway' from needs human) do not block Approve & merge. It is not stated whether this is intended.

**Remedy**

> State explicitly whether failing tested or reviewed sub-signals block merge, show a warning, or are covered only by item approval, and list them among the unmet conditions if they gate.

### R2-13 — consistency

**Problem**

> Problem statement step 5 (the user's requirement) says a stop lets the in-flight task finish, and the coaching note praises that phrasing, but the soft stop parks the task at the next phase boundary instead of finishing it. The deviation from the stated requirement is not acknowledged.

**Remedy**

> Either make soft stop finish the whole task (with the per-task budget as the bound) or record the phase-boundary behavior as a deliberate change to requirement 5 with its rationale for user approval.

### R2-14 — clarity

**Problem**

> The plan is re-rendered into the PR description on every revision, which silently overwrites any edits made to the description on GitHub; the behavior is unstated. Step 8 questions also run 'outside run windows', which can be read as only outside windows rather than regardless of windows.

**Remedy**

> State that codeboost owns the PR description (or a delimited section of it) and what happens to external edits, and reword the question rule to 'regardless of run windows'.

### R2-15 — feasibility

**Problem**

> The decision gate runs after slice 2, before the executor exists, but the real-PR test needs a PR whose commits carry Plan-Item trailers. How that PR is produced is unstated. The user also plants the out-of-scope edit and then reviews the same PR, so catching a plant whose location they already know proves little.

**Remedy**

> State that gate PRs are produced by the manual per-item protocol from The Assignment, and have someone else plant the out-of-scope edit (or plant it by script at a random location unknown to the reviewer) in both PRs.

### R2-16 — consistency

**Problem**

> The MSR '26 study of unmerged bug-fix PRs is still cited without title, authors, or link, and the arXiv 2601.15195 claim links to alphaxiv.org rather than arxiv.org; the specific findings attributed to both could not be verified from the document.

**Remedy**

> Add a full citation and link for the MSR '26 study and use the canonical arxiv.org URL, or remove the attribution and keep the claim only as a hypothesis.

### R2-17 — feasibility

**Problem**

> node:sqlite is still experimental in Node 22.x (it prints an ExperimentalWarning and its API can change in minor releases), which is a stability risk for the single source of truth. Detecting branch protection 'when a repo is added' may also require admin permission for the protection API, so the detection can fail for non-admin collaborators.

**Remedy**

> Pin a tested Node version range and isolate SQLite access behind a small storage module (with better-sqlite3 or a WASM build as fallback), and define the branch-protection detection method (rulesets API vs protection API) and its behavior when permission is denied.
